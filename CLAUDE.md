# StageHopper — working notes

A SvelteKit SPA (`adapter-static`, `fallback: index.html`) on S3 + CloudFront, an API Gateway
HTTP API in front of one `stagehopper` Lambda, and DynamoDB as the write-side source of
truth. Everything a signed-out visitor reads is a **derived JSON file in the site bucket**,
not an API call.

The traps below have each shipped a silently-broken feature at least once. They are not
obvious from the code, which is why they are here.

## 1. An unmatched path answers `200 text/html`, not 404

CloudFront serves `index.html` for anything that isn't a real object — that's how SPA deep
links work. So "the URL returns `<!doctype html>`" is **normal** for `/festival/{id}` and
`/room/{roomId}`, and is **the failure signature** for anything that was supposed to be a
file or an API route. There is no 404 to notice; the response looks fine and is 200.

Diagnose by content type, never by status:

```bash
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' -X POST -d '{}' https://stagehopper.radomskyi.com/api/stagehopper/admin/festivals
```

`application/json` (a 401 from the JWT authorizer counts) means the route is wired.
`text/html` means it is not.

## 2. Every API route is declared twice — and one of them is in another repo

Adding a `case` to the Lambda's route switch is half the change. The matching
`aws_apigatewayv2_route` lives in the separate **infrastructure** (Terraform) repo, under
`projects/stagehopper/`. Miss it and requests fall through to trap 1: the client gets HTML,
parses it as JSON, and reports a generic failure.

`deploy.yml`'s "Smoke-test API routes reach the Lambda" step probes every route for this.
**Add each new route to that list in the same PR** — the check only covers what it is told
about.

The same split applies to anything else the Lambda reads from its environment. A new
DynamoDB table is a `resource`, an ARN in the IAM policy, *and* an entry in the function's
`environment.variables` — all three in the infrastructure repo, none of them in this one.
Apply that before tagging a release that uses the table: `ROOMS_TABLE` is written inside the
transaction that saves a room's selections, so shipping the app first would not degrade a
feature, it would stop every pick-save outright.

## 3. Public JSON is a whitelist, rebuilt only on an admin write

`data/festivals/index.json` is generated by `publishFestivalsManifest()` in
[lambda/index.ts](lambda/index.ts) from the `stagehopper-festivals` table, field by
explicit field. Two independent failure modes:

- **The field isn't in the whitelist.** Adding it to `FestivalRecord`, validating it, and
  storing it in DynamoDB gets it as far as the admin form and no further. It must also be
  in `FestivalManifestEntry` *and* in the object the builder maps. `mapUrl` was missed for
  the whole life of the manifest, which is why the room's Map menu entry never appeared for
  anyone even though the map uploaded, stored, and previewed correctly.
- **The published file is older than the code.** The manifest is rewritten only when an
  admin saves a festival. A release that starts publishing a new field leaves the live file
  in its old shape until somebody happens to make an unrelated edit — that is how
  `description` stayed missing from the festival page for a full release. `deploy.yml` now
  fixes this by invoking the Lambda directly with `{"republish":"festivals-manifest"}` right
  after updating the function code (see [docs/manifest-republish-infra.md](docs/manifest-republish-infra.md)
  for the one IAM statement that permits it).

When a field looks missing in the browser, read the published file before reading any code:

```bash
curl -s https://stagehopper.radomskyi.com/data/festivals/index.json
```

Compare it against the DynamoDB row (`aws dynamodb get-item --region eu-central-1
--table-name stagehopper-festivals --key '{"id":{"S":"<festivalId>"}}'`). Present in the
table and absent from the file localizes the bug to the publisher in one step.

Per-festival timetables (`data/festivals/{id}/timetable.json`) work the same way but are
*not* republished on deploy: rebuilding one for a festival with no performances would
create an empty `days: []` file where the app expects a 404.

## 4. `deploy.yml` never syncs `data/*`

Every S3 sync excludes it, so a deploy can't clobber an admin's edits — and equally can't
seed them. Until the first admin save creates `data/festivals/index.json`, the live
festival list is the compiled `DEFAULT_FESTIVALS` in
[src/lib/stagehopper/festivals.svelte.ts](src/lib/stagehopper/festivals.svelte.ts).

## 5. Deploys happen on a `v*` tag, not on merge to main

Pushing to `main` ships nothing. Commits sitting on `main` past the newest tag are not
live — check `git tag --sort=-creatordate | head -1` against `origin/main` before concluding
that deployed behaviour contradicts the source.

## 6. The service worker decides what a returning visitor sees

[static/sw.js](static/sw.js) is cache-first for `/data/*` with background revalidation, so
**an admin edit shows up on the load after the next one**, not immediately. It must be
uploaded with `Cache-Control: no-cache` (deploy.yml uses `aws s3 cp`, not `sync`, precisely
because sync skips a byte-identical file and leaves stale headers on it). A stale worker
pinned in an edge or on a device is the first thing to rule out for "the fix didn't reach
my phone".

## 7. CloudFront strips request headers it isn't told to forward

The `/api/*` behaviour forwards only whitelisted headers. Anything new the client sends —
`Authorization` included — has to be added to the cache/origin-request policy in the
infrastructure repo, or it silently never reaches the Lambda.
